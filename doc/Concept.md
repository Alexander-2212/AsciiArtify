# Concept: вибір інструменту для локального Kubernetes-кластера

**Проєкт:** AsciiArtify - перетворення зображень в ASCII-art за допомогою ML
**Статус:** PoC / Concept
**Автор:** Oleksandr Kaminskyi
**Дата:** серпень 2026

---

## 1. Вступ

Команді AsciiArtify потрібне локальне середовище розробки на базі Kubernetes: розробник має мати змогу підняти кластер на власній машині, розгорнути туди свій сервіс і перевірити його поведінку до того, як код потрапить у CI та на спільні середовища.

Оскільки продакшн планується на Kubernetes, локальне середовище має бути максимально близьким до нього за API та поведінкою, але при цьому - легким, швидким і безкоштовним.

Розглядаються три інструменти:

| Інструмент | Що це | Розробник |
|---|---|---|
| **minikube** | Локальний кластер у VM або контейнері, з системою аддонів | Kubernetes SIGs |
| **kind** | Kubernetes IN Docker - ноди кластера як Docker-контейнери | Kubernetes SIG Testing |
| **k3d** | Обгортка над k3s (легкий дистрибутив Kubernetes від Rancher/SUSE), ноди як Docker-контейнери | k3d-io / SUSE |

Окремо розглядається **ризик ліцензування Docker Desktop** і можливість переходу на **Podman** як безкоштовну альтернативу.

## 2. Характеристики

| Характеристика | minikube | kind | k3d |
|---|---|---|---|
| Тип ізоляції | VM або контейнер (за вибором драйвера) | Docker/Podman-контейнер | Docker/Podman-контейнер |
| Підтримувані ОС | Linux, macOS, Windows | Linux, macOS, Windows | Linux, macOS, Windows |
| Архітектури | x86_64, arm64 | x86_64, arm64 | x86_64, arm64 |
| Драйвери / backend | docker, podman, kvm2, hyperkit, hyper-v, virtualbox, ssh, none | docker, podman (експериментально), nerdctl | docker, podman (експериментально) |
| Дистрибутив Kubernetes | vanilla (kubeadm) | vanilla (kubeadm), використовується для conformance-тестів самого Kubernetes | k3s (сумісний, але урізаний) |
| Multi-node | так (`--nodes N`) | так (через `kind-config.yaml`) | так (`--servers N --agents M`) |
| Час старту (1 нода, орієнтовно) | 60–120 с | 30–60 с | 15–30 с |
| Споживання RAM (орієнтовно) | 2 ГБ+ (VM-драйвери), ~1 ГБ (docker) | ~700 МБ | ~400–500 МБ |
| Ingress | аддон (`minikube addons enable ingress`) | встановлюється вручну + `extraPortMappings` | Traefik з коробки |
| LoadBalancer-сервіси | `minikube tunnel` | не підтримується без MetalLB | klipper-lb з коробки |
| Локальний registry | аддон `registry` | вручну (контейнер + `containerdConfigPatches`) | `k3d registry create` |
| Завантаження локального образу | `minikube image load` | `kind load docker-image` | `k3d image import` |
| Автоматизація / CI | так, є `--wait`, profiles | так, де-факто стандарт для GitHub Actions | так, декларативний `k3d.yaml` |
| Додаткові інструменти | dashboard, metrics-server, registry, ingress, csi-hostpath - понад 30 аддонів | немає, все ставиться руками | Traefik, ServiceLB, local-path-provisioner, metrics-server, CoreDNS |
| Керування кластером | `minikube` CLI + dashboard | `kind` CLI | `k3d` CLI + плагін для VS Code |
| Ліцензія | Apache 2.0 | Apache 2.0 | MIT (k3d), Apache 2.0 (k3s) |

## 2.1 Матриця порівняння

Оцінювання за шкалою **1–3** (1 - не задовольняє, 2 - задовольняє з обмеженнями, 3 - повністю задовольняє). Вага критерію відображає його важливість **саме для сценарію локальної розробки PoC AsciiArtify** - для іншого сценарію ваги будуть іншими (див. примітку нижче).

| # | Критерій | Вага | minikube | kind | k3d |
|---|---|:---:|:---:|:---:|:---:|
| 1 | Швидкість створення кластера | 3 | 2 | 1 | **3** |
| 2 | Споживання ресурсів хоста | 3 | 2 | **3** | 2 |
| 3 | Відповідність vanilla Kubernetes | 2 | **3** | **3** | 1 |
| 4 | Ingress «з коробки» | 3 | 2 | 1 | **3** |
| 5 | Підтримка сервісів типу LoadBalancer | 2 | 2 | 1 | **3** |
| 6 | Простота multi-node конфігурації | 2 | 2 | 2 | **3** |
| 7 | Локальний registry / імпорт образів | 2 | 2 | 2 | **3** |
| 8 | Складність початкового налаштування | 3 | **3** | 2 | **3** |
| 9 | Придатність для CI-пайплайну | 2 | 1 | **3** | 2 |
| 10 | Незалежність від Docker Desktop | 3 | **3** | 2 | 2 |
| 11 | Документація та спільнота | 1 | **3** | **3** | 2 |
| 12 | Контроль версії Kubernetes | 2 | **3** | **3** | 2 |
| | **Зважений підсумок** | | **65** | **58** | **69** |
| | *максимум можливий* | | *84* | *84* | *84* |

### Обґрунтування ключових оцінок

| Критерій | Коментар |
|---|---|
| 1. Швидкість | Заміряно на однакових умовах: k3d 13.5 с, minikube 26.1 с, kind 31.4 с (K8s v1.32.2, 1 нода, теплий кеш). У kind і minikube у цей час входить очікування готовності control-plane, у k3d - ні, тож реальний розрив менший за номінальний. |
| 2. Ресурси | kind 527 МБ, minikube 509 МБ, k3d 667 МБ. Але у 667 МБ k3d вже входять Traefik, ServiceLB, metrics-server і local-path-provisioner, яких у kind немає взагалі. minikube отримує 2 замість 3 через ~800 МБ образів на першому запуску (preload + kicbase). |
| 3. Vanilla | kind і minikube збирають кластер через kubeadm. k3s замінює etcd на SQLite, вилучає in-tree cloud providers і частину alpha-фіч - для stateless HTTP-сервісу різниці немає, але формально це не vanilla. |
| 4, 5. Ingress / LB | k3d - працює одразу після `cluster create`. minikube - один аддон (`addons enable ingress`) плюс `minikube tunnel` для LB. kind - ручна установка ingress-nginx і `extraPortMappings`, який неможливо додати без перестворення кластера. |
| 9. CI | kind - де-факто стандарт для GitHub Actions і conformance-тестів самого Kubernetes. minikube в CI використовується рідко через вагу й час старту. |
| 10. Docker Desktop | minikube єдиний, хто вміє працювати взагалі без контейнерного рантайму (драйвери kvm2/hyperkit). kind і k3d потребують Docker або Podman, причому підтримка Podman в обох позначена як експериментальна. |

### Примітка щодо ваг

Ваги підібрано під сценарій **локальної розробки**, де вирішальні швидкість ітерації та готовність мережевого стека. Якщо переставити ваги під сценарій **e2e-тестів у CI** - підняти критерії 3 (відповідність vanilla), 9 (придатність для CI) і 12 (контроль версії) до ваги 3, а критерії 1, 4, 5 опустити до 1 - лідером стає **kind**.

Саме тому підсумкове рішення не зводиться до одного інструменту: **k3d для локальної розробки, kind для CI** (див. розділ 6).

## 3. Переваги та недоліки

### 3.1 minikube

**Переваги**
- Найбільш «повнофункціональний»: аддони закривають ingress, registry, metrics, dashboard однією командою.
- Єдиний з трьох, хто вміє працювати **без контейнерного рантайму на хості** - драйвери kvm2/hyperkit/hyper-v/virtualbox. Це прямий обхід проблеми ліцензування Docker Desktop.
- Вбудований GUI-дашборд - низький поріг входу для команди без DevOps-досвіду.
- Найдовша історія та найбільша база документації і Stack Overflow-відповідей.

**Недоліки**
- Найважчий і найповільніший, особливо на VM-драйверах.
- Multi-node підтримується, але історично найменш стабільний із трьох.
- Аддони - зручність ціною відходу від «як у продакшні»: конфігурація ingress-контролера відрізняється від того, що буде в хмарі.

### 3.2 kind

**Переваги**
- Vanilla Kubernetes, зібраний тим самим kubeadm - **найточніша відповідність продакшн-поведінці**. Проєкт Kubernetes сам ганяє на ньому свої conformance-тести.
- Прозорий декларативний конфіг multi-node кластера (кілька control-plane нод для перевірки HA-сценаріїв).
- Де-факто стандарт для e2e-тестів у CI: майже в кожному GitHub Actions пайплайні з Kubernetes саме kind.
- Найпередбачуваніша поведінка при оновленні версій Kubernetes (`--image kindest/node:v1.32.x`).

**Недоліки**
- Мінімалізм: ingress, registry, storage - все руками. Стартовий сетап найдовший.
- Проброс портів фіксується **на етапі створення кластера** (`extraPortMappings`), додати порт потім = перестворити кластер.
- Немає підтримки сервісів типу LoadBalancer без MetalLB.

### 3.3 k3d

**Переваги**
- Найшвидший старт і найменше споживання ресурсів - критично, якщо на тій самій машині крутиться ML-навантаження.
- Ingress (Traefik) і LoadBalancer (klipper-lb) працюють одразу після `k3d cluster create` - «Hello World» доступний за localhost без додаткових кроків.
- Вбудований локальний registry однією командою - зручно для швидкого циклу build → push → deploy.
- Multi-node без окремого конфіг-файлу, прямо у прапорцях CLI.

**Недоліки**
- k3s **не є** vanilla Kubernetes: SQLite замість etcd за замовчуванням, замінений service LB, вилучені альфа-фічі та in-tree cloud providers. Для більшості додатків різниці немає, але при роботі з низькорівневими речами (CSI, cloud-controller, специфічні admission-плагіни) локальна поведінка може розійтися з продакшн.
- Traefik з коробки - плюс для швидкого старту, мінус якщо в продакшні nginx або Gateway API: доведеться вимикати (`--k3s-arg '--disable=traefik@server:*'`).
- Найменше community порівняно з minikube/kind.

## 4. Ризик ліцензування Docker та альтернатива Podman

### 4.1 Суть ризику

Docker Desktop розповсюджується за Docker Subscription Service Agreement. Безкоштовне використання обмежене: <cite index="10-1">без платної підписки Docker Desktop дозволено використовувати лише для некомерційних open source проєктів або в комерційній організації з менш ніж 250 співробітниками та річним доходом менше 10 млн доларів США</cite>. <cite index="13-1">Державні установи потребують підписки незалежно від розміру.</cite>

Для AsciiArtify на етапі стартапу з двох людей ризику **немає** - компанія підпадає під безкоштовне використання. Ризик відкладений і спрацьовує у двох сценаріях:

1. Компанія росте або її купує більший гравець - усі робочі станції розробників миттєво стають нелегальними без оплати підписки на кожного користувача.
2. Продукт продається корпоративному замовнику, який захоче відтворити середовище розробки у себе - а він майже напевно перевищує пороги.

Важливо: обмеження стосується **лише Docker Desktop** як застосунку. Docker Engine (dockerd) на Linux під Apache 2.0 і залишається безкоштовним. Тобто на Linux-машинах ризику немає взагалі, він актуальний для розробників на macOS та Windows.

### 4.2 Podman як альтернатива

Podman - daemonless-рантайм від Red Hat під Apache 2.0, без обмежень на комерційне використання, з rootless-режимом за замовчуванням і Docker-сумісним CLI та API.

Сумісність із розглянутими інструментами:

| Інструмент | Підтримка Podman | Примітки |
|---|---|---|
| minikube | `--driver=podman` | Найбільш зрілий шлях; альтернативно взагалі обійти контейнери через `--driver=kvm2` |
| kind | <cite index="16-1">`KIND_EXPERIMENTAL_PROVIDER=podman kind create cluster`, підтримується rootless Podman на хостах з cgroup v2</cite> | Позначено як експериментальне, але на практиці стабільне |
| k3d | Через шар Docker API-сумісності | <cite index="17-1">k3d використовує Docker API та сумісний з Podman v4 і вище, але підтримка позначена як експериментальна і робота не гарантується</cite>; потрібно увімкнути `podman.socket`, зняти таймаут сервісу та створити symlink на `/var/run/docker.sock` |

**Висновок щодо ризику:** він керований і не є блокером. Найдешевша страховка - не зашивати Docker Desktop у документацію та скрипти, а працювати через змінну `DOCKER_HOST` і абстрагувати рантайм у Makefile. Тоді перехід на Podman - це зміна однієї змінної оточення, а не переписування процесів.

## 5. Демонстрація

**Рекомендований інструмент: k3d.**

Демо: розгортання застосунку та перевірка доступності через Ingress на свіжому кластері.

```bash
# 1. Кластер: 1 server + 2 agents, порт 80 loadbalancer'а прокинуто на localhost:8080
k3d cluster create asciiartify \
  --servers 1 \
  --agents 2 \
  -p "8080:80@loadbalancer"

# 2. Перевірка нод - kubeconfig k3d підставляє автоматично
kubectl get nodes -o wide

# 3. Розгортання застосунку
kubectl create deployment hello --image=traefik/whoami --replicas=3
kubectl expose deployment hello --port=80

# 4. Ingress (Traefik уже працює з коробки, встановлювати нічого не треба)
kubectl create ingress hello \
  --rule="localhost/*=hello:80"

# 5. Перевірка: відповідають різні поди - балансування працює
curl -s http://localhost:8080 | grep Hostname
curl -s http://localhost:8080 | grep Hostname

# 6. Прибирання
k3d cluster delete asciiartify
```

## 6. Висновки

| Сценарій | Рекомендація |
|---|---|
| **Локальна розробка (PoC AsciiArtify)** | **k3d** - швидкий старт, мінімум ресурсів, ingress і LB з коробки |
| **E2E-тести в CI** | **kind** - vanilla Kubernetes, передбачувані версії, стандарт для GitHub Actions |
| **Онбординг / демо замовнику** | **minikube** - дашборд і аддони, найнижчий поріг входу |

**Рішення для AsciiArtify:**

1. **k3d** як основний інструмент локальної розробки. Для ML-продукту вирішальним є те, що кластер залишає максимум вільної RAM і CPU під саме навантаження, а не під інфраструктуру. Ризик розходження k3s із vanilla Kubernetes на етапі PoC несуттєвий: застосунок - це stateless HTTP-сервіс з ML-інференсом, без екзотики на рівні CSI чи cloud-controller.
2. **kind** у CI-пайплайні для e2e-тестів - там, де важлива точна відповідність продакшн-версії Kubernetes, а не швидкість старту.
3. **minikube** не використовувати як основний інструмент, але тримати в документації як запасний варіант: його VM-драйвери (kvm2/hyperkit) - єдиний спосіб працювати взагалі без контейнерного рантайму на хості.
4. **Ліцензування Docker:** зараз ризику немає, але конфігурацію одразу писати рантайм-агностично (`DOCKER_HOST`, обгортки в Makefile), щоб міграція на Podman коштувала години, а не тижня.
5. Зафіксувати версію Kubernetes у декларативному `k3d.yaml` і тримати її синхронною з версією продакшн-кластера.
